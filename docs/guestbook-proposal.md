# NICE FAITH 방명록 기획안

작성일: 2026-11-05 · 상태: 기능 기획 제안, Firestore·서울·무료 운영·콘솔 관리 선정 · 범위: 첫 출시

## 1. 목적과 방향

앱을 경험한 개인, 교회·모임, 방문자가 짧은 소감과 방문의 흔적을 남기는 공간을 만든다. 사용자에게는 함께 돌아본 사람들의 이야기를, 제작자에게는 실제 활용 맥락과 개선 단서를 제공한다.

사용자에게 보이는 이름은 **발자취**를 권장한다. 신앙을 평가하는 점수에서 은혜에 대한 성찰로 이어지는 앱의 메시지를 유지하며, 인기나 신앙 수준을 비교하는 공간으로 만들지 않는다.

대표 문구:

> 함께 돌아본 우리의 발자취
>
> 혼자 잠시 들렀어도, 공동체와 함께 사용했어도 괜찮아요. 마음에 남은 한 문장을 남겨 주세요.

## 2. 이용 대상

| 대상 | 남기고 싶은 내용 | 표시 예시 |
| --- | --- | --- |
| 개인 | 사용 소감, 마음에 남은 질문 | 봄날 · 개인 |
| 교회·모임 참여자 | 공동체에서 사용한 경험 | 하준 · ○○교회 청년부 |
| 방문자 | 인사, 응원, 짧은 의견 | 이름 없는 방문자 · 방문 |

교회·모임명은 선택 입력이며 본인 기재 정보다. 교회 공식 참여, 제휴, 추천 또는 대표자 인증으로 표시하지 않는다. 개인·방문자 구분도 본인 선택이며 설문 완료 여부를 검증하지 않는다.

## 3. 진입 위치와 사용자 흐름

### 진입 위치

- **성찰 화면:** 개인화 성찰과 돌아볼 질문을 읽은 뒤, 공유 영역 앞에 ‘마음에 남은 한 문장 남기기’를 배치한다. 첫 출시의 주요 작성 진입점이다.
- **첫 화면 하단:** ‘함께 돌아본 발자취’ 링크를 제공한다. 설문을 하지 않은 방문자도 읽고 쓸 수 있다.
- **독립 화면 `#/guestbook`:** 새로고침과 직접 접근이 가능하다. 기존 설문 답변은 같은 탭에서 오가는 동안 유지한다.

리포트와 점수 소멸 연출 중에는 방명록 작성을 유도하지 않는다. 첫 화면에서는 소감을 미리 노출하지 않고 링크만 제공해 핵심 메시지를 먼저 경험하도록 한다. 방명록 자체는 공개 공간이므로 직접 방문하면 성찰 내용이 보일 수 있다.

### 작성 흐름

1. 발자취 화면에서 공개 글을 읽거나 ‘발자취 남기기’를 선택한다.
2. 작성 폼과 공개 안내를 확인한다.
3. 내용을 입력하고 공개 동의 후 등록한다.
4. ‘발자취를 남겼습니다. 운영자 확인 후 공개됩니다.’를 표시한다.
5. 작성자에게 삭제용 비공개 링크를 한 번 제공하고 보관을 안내한다.
6. 운영자가 승인한 글만 공개 목록에 나타난다.

방문자는 로그인 없이 이용한다. 등록 실패 시 폼을 유지하며 다시 시도할 수 있다. 제출 중 중복 클릭을 막고, 서버도 동일 등록 요청의 재전송을 중복 저장하지 않는다. 작성 중 이동하려는 경우 내용이 사라진다는 안내를 제공하며, 새로고침 시에는 브라우저가 지원하는 이탈 경고를 사용한다. 초안은 브라우저 저장소에 저장하지 않는다.

## 4. 작성 폼

| 항목 | 필수 | 기준 |
| --- | --- | --- |
| 방문 유형 | 예 | 개인 / 교회·모임과 함께 / 잠시 방문. 기본값은 개인 |
| 별명 | 아니요 | 최대 20자. 공란이면 ‘이름 없는 방문자’ |
| 교회·모임명 | 아니요 | ‘교회·모임과 함께’ 선택 시 표시. 최대 40자 |
| 한마디 | 예 | 공백 제거 후 1~300자, 줄바꿈 허용 |
| 공개 동의 | 예 | 미리 선택하지 않음. 별명·모임명·내용·작성일의 공개와 운영 목적 저장 안내 |

모임명 없이도 공동체 참여 소감을 남길 수 있다. 유형을 바꾸면 숨겨진 모임명은 제출하지 않는다. 글자 수 기준은 화면과 서버에서 동일하게 적용한다.

내용 입력 예시:

> 오늘 어떤 마음이 남았나요? 함께 사용한 이야기나 짧은 인사를 남겨 주세요.

공개 안내:

> 승인된 글은 누구나 볼 수 있습니다. 실명, 연락처, 다른 사람의 개인정보나 민감한 신앙 상담 내용은 적지 말아 주세요. 교회·모임명은 공개해도 괜찮은 경우에만 입력해 주세요.

> 민감한 내용이 포함되어있는 경우, 관리자가 임의로 삭제할 수 있습니다

입력값은 일반 텍스트로 취급한다. HTML, 이미지, 첨부파일, 링크 삽입 기능은 제공하지 않으며, 본문 속 주소도 클릭 가능한 링크로 만들지 않는다. 오류는 해당 필드 옆에서 설명하고 입력한 내용을 유지한다.

## 5. 공개 목록

- 승인된 글을 최신순으로 20개씩 제공하고 ‘더 보기’로 추가 조회한다.
- 카드에는 별명, 방문 유형 또는 모임명, 내용, 작성일, 신고 버튼을 표시한다. 모임명이 없으면 ‘교회·모임과 함께’로 표시한다.
- 작성일은 한국 시간의 날짜만 공개한다.
- 첫 글이 없으면 ‘아직 첫 발자취를 기다리고 있어요.’와 작성 버튼을 표시한다.
- 목록 로딩 실패 시 오류와 재시도 버튼을 제공하고, 빈 목록으로 오인하게 표시하지 않는다.
- 글별 공개 상세 주소, 검색, 유형별 필터는 첫 출시에 포함하지 않는다.

표시 예시:

> **봄날** · ○○교회 청년부 · 2026.11.05
>
> 청년부에서 함께 해봤어요. 마지막 질문을 가지고 서로 이야기 나눴습니다.

점수·등급, 좋아요, 댓글, 인기순, 교회별 순위, 참여 교회 수는 표시하지 않는다. 소속이 없는 사용자에게도 같은 비중으로 글을 보여준다.

## 6. 공개·관리 정책

**첫 출시는 운영자 승인 후 공개를 권장한다.** 로그인 없는 공개 입력 공간의 광고, 개인정보 노출, 비방을 줄이기 위한 선택이다. 운영자 검토 부담과 공개 지연이 생기므로 운영자가 정기적으로 확인할 수 있을 때 출시한다. 화면에 즉시 공개를 약속하지 않는다.

### 상태와 권한

- 신규 글은 `pending`으로 저장한다.
- 운영자는 Firebase 콘솔에서 직접 승인 시 `published`, 거절 또는 공개 중단 시 `hidden`으로 전환한다. 승인 시 `publishedAt`을 기록하고 `expiresAt`을 제거한다. 숨김 시 `expiresAt`을 처리 시각으로부터 30일 뒤로 설정한다.
- 작성자 삭제 또는 운영자 영구 삭제 시 본문과 식별 가능한 입력값을 삭제한다. 상태만 바꾸고 내용을 무기한 보관하지 않는다.
- 일반 방문자는 승인된 글만 조회한다. 대기 글·숨긴 글·삭제 링크·운영 정보는 공개 API에서 반환하지 않는다.
- 앱 내 관리자 화면·관리 API·Firebase Authentication은 만들지 않는다. 운영자는 본인의 Google 계정과 프로젝트 IAM 권한으로 Firebase 콘솔에 접근한다. 계정에 2단계 인증을 적용하고 서비스 계정 자격 증명과 구분한다.
- 운영자는 원문을 고쳐 공개하지 않는다. 문제가 있으면 숨김 또는 삭제한다.

공개 허용: 사용 소감, 방문 인사, 응원, 정중한 비판과 개선 의견.

비공개 대상: 광고·도배, 혐오·욕설·비방, 다른 사람의 신앙 평가, 개인정보 노출, 민감한 상담·고백 내용, 사칭, 주제와 무관한 내용. 단순히 부정적인 의견이라는 이유로 숨기지 않는다.

### 삭제와 신고

- 작성자에게 추측하기 어려운 삭제 토큰이 포함된 비공개 링크를 제공한다. 서버에는 토큰 원문 대신 해시를 보관한다.
- 삭제 링크 방문만으로 삭제하지 않는다. 확인 후 명시적인 삭제 요청을 보낼 때 처리해 링크 미리보기 등으로 인한 삭제를 막는다.
- 토큰은 공개 목록·접근 로그·분석 수집에 노출하지 않는다. 삭제 페이지에는 외부 리소스를 두지 않고 `no-referrer` 정책을 적용한다.
- 링크를 잃어버린 경우 앱의 운영 문의 경로로 삭제를 요청할 수 있다. 운영자가 확인 후 처리하며 민감한 증빙을 공개 댓글로 요구하지 않는다.
- 신고는 사유 선택으로 접수한다. 개인정보 노출 / 광고·도배 / 비방·부적절한 내용 / 기타. 같은 글의 반복 신고를 제한한다.
- 신고만으로 자동 삭제하지 않는다. 운영자가 검토하며 필요하면 즉시 숨긴다.
- 운영자는 Firebase 콘솔의 글 컬렉션을 상태별로 조회하고 신고 컬렉션을 확인해 승인·숨김·영구 삭제한다. 원문과 서버 검증용 필드는 변경하지 않는다. 콘솔에서 영구 삭제할 때는 연결 신고도 함께 삭제한다.

## 7. 개인정보와 보관

현재 앱은 설문 답변을 메모리에만 보관한다. 방명록은 사용자가 선택해서 공개 정보를 서버에 저장하는 별도 기능이다.

- 설문 답변, 점수, 개인화 성찰을 방명록과 연결하거나 자동 전송하지 않는다.
- 이메일, 전화번호, 생년월일, 위치, 교회 주소를 받지 않는다.
- 교회 소속은 신앙 관련 정보를 드러낼 수 있으므로 입력을 유도하거나 필수화하지 않는다.
- 거절·숨김 글은 30일, 승인 대기 글은 30일 후 자동 삭제를 제안한다. 공개 글은 삭제 요청 또는 서비스 종료까지 보관한다.
- 방어 목적으로 IP 기반 식별이 필요하면 원문을 방명록 DB에 저장하지 않고, 회전하는 비밀값을 사용한 해시 등으로 단기 처리한다. 해당 식별값과 요청 제한 기록은 24시간 이내 논리 만료하며 일일 정리 작업에서 물리 삭제한다. 정상 실행 시 생성 후 최대 약 48시간과 스케줄 지연 동안 남을 수 있다. 정리 실패 시 운영자가 재실행하며 이 실제 보관 방식을 개인정보 안내에 명시한다.
- 호스팅·DB의 접근 로그와 백업에 남는 정보 및 보관 기간도 확인해 안내한다. 영구 삭제 시 백업에서 사라지는 시점까지 정책에 명시한다.
- 공개 전 개인정보 안내와 README의 ‘데이터베이스를 사용하지 않음’ 등 기존 설명을 실제 동작에 맞게 갱신한다.

위 보관 기간은 제안값이다. 출시 전에 실제 인프라 설정과 운영 책임자를 확정한다.

## 8. 구현 방향과 경계

현재 SolidJS 화면·해시 라우팅·Vercel Function 구성을 확장하고, 방명록 영속 저장소로 **Cloud Firestore Standard edition**을 사용한다. Firebase Hosting이나 Cloud Functions로 기존 배포를 옮기지 않는다. Firebase 프로젝트·DB 생성과 연결은 아직 진행하지 않은 상태다.

```text
방문자 → SolidJS 화면 → Vercel Function → Firestore
운영자 → Google 계정·프로젝트 IAM → Firebase 콘솔 → Firestore
```

브라우저는 Firestore에 직접 접근하지 않는다. Vercel 서버에서 Firebase Admin SDK로 조회·저장하며, 공개 응답은 승인된 글의 허용 필드만 골라 반환한다. 방문자에게 Firebase 계정이나 익명 로그인을 요구하지 않는다. 운영 작업은 Firebase 콘솔에서 직접 수행하며 별도 관리자 로그인 기능은 구현하지 않는다.

### 최소 구성

- 방명록 목록·작성 화면과 기존 화면의 진입 링크
- 서버의 공개 목록 조회, 등록, 작성자 삭제, 신고 API
- Firestore의 글·신고 저장과 만료 정리
- Firebase 콘솔에서 사용할 승인·숨김·삭제 절차 문서

### Firestore 저장 구조

| 컬렉션 | 저장 정보 | 접근 |
| --- | --- | --- |
| `guestbookEntries` | 방문 유형, 별명, 선택 모임명, 본문, 공개 상태, 작성·승인 시각, 삭제 토큰 해시, 만료 시각 | 서버 전용. 공개 API는 승인된 글의 표시 필드만 반환 |
| `guestbookReports` | 대상 글 ID, 신고 사유, 접수 시각, 처리 상태, 만료 시각 | 서버 및 콘솔의 권한 있는 운영자 전용 |
| `guestbookRequestGuards` | 단기 요청 제한 카운터, 중복 요청 식별값, 만료 시각 | 서버 전용 |

글 ID는 자동 생성 등 추측하기 어려운 값으로 정한다. 작성 시각과 초기 공개 상태는 서버가 결정하고, 이후 공개 상태·승인 시각·만료 시각만 운영자가 콘솔에서 변경한다. 별도 운영 로그 컬렉션이나 콘솔 수정 감지용 Cloud Functions는 만들지 않는다. 콘솔 변경의 앱 자체 감사 이력은 첫 출시에서 제공하지 않는다. 서버를 통한 글 삭제 시 연결된 신고도 정리하고, 콘솔 직접 삭제로 남은 신고는 일일 정리 작업에서 제거한다. 중복 요청 기록의 보관 기간은 출시 전 확정한다.

### 목록 조회와 동시 처리

- 공개 목록은 `status == published` 조건과 작성 시각 내림차순을 사용한다. 동일 시각의 글은 문서 ID로 순서를 고정한다.
- 20개씩 커서 기반 페이지 조회를 사용한다. 전체 문서를 읽어 화면에서 자르거나 offset으로 넘기지 않는다.
- 해당 조회에 필요한 복합 인덱스를 저장소에서 관리하고 배포 절차에 포함한다.
- 첫 출시는 실시간 구독을 사용하지 않는다. 화면 진입·더 보기·명시적 재시도 시 조회한다.
- 등록과 중복 요청 기록, 요청 제한 카운터는 필요한 범위에서 Firestore 트랜잭션으로 일관성을 보장한다. 응답 유실 후 같은 요청을 재시도해도 글과 작성자의 삭제 권한을 복구할 수 있게 설계한다.
- 콘솔 승인·숨김은 기존 문서만 수정한다. 삭제 후 동일 ID 문서를 재생성하지 않는다. 공개 조회는 문서의 허용 상태와 만료 여부를 확인해 실수로 승인된 만료 글도 노출하지 않는다.

### 권한과 배포 설정

- Firestore Security Rules는 웹·모바일 클라이언트의 직접 읽기·쓰기를 모두 거절한다.
- Admin SDK 요청은 Security Rules를 우회하므로, 공개 API의 검증·공개 조건·작성자 삭제 권한 검사는 Vercel 서버에서 수행한다. 운영자 접근은 Google 계정·프로젝트 IAM으로 제한한다. 서버 자격 증명에는 필요한 IAM 권한만 부여한다.
- 자격 증명은 Vercel의 서버 전용 비밀 설정으로 관리한다. `VITE_` 환경변수, 프런트 번들, Git에 넣지 않는다.
- 개발·미리보기 환경이 운영 DB를 수정하지 않게 분리한다. 로컬 테스트는 Firestore Emulator를 사용한다.
- Firestore 저장 지역은 **서울 `asia-northeast3`**로 확정한다. `asia-northeast2`는 오사카다. 생성 화면에서 서울을 확인한 뒤 만든다. Vercel 함수 지역은 사용 플랜의 지원 범위에서 가까운 지역으로 설정한다.

### 비용과 보관 기한 처리

- 비용은 문서 읽기·쓰기·삭제, 일부 인덱스 읽기, 저장·전송량에 따라 발생한다. 방어용 카운터와 중복 확인도 사용량에 포함한다.
- 목표 지출은 **월 0원**, 운영 예산은 **월 1,000원**으로 기록한다. 사용자가 기간을 지정하지 않아 월 기준으로 정리했다. 무료 운영을 우선하고 예산이 있다고 자동으로 유료 전환하지 않는다.
- Firebase는 **Spark 무료 플랜**으로 시작하고 Cloud Billing 계정을 연결하지 않는다. 현재 무료 할당량은 저장 1 GiB, 하루 읽기 50,000건·쓰기 20,000건·삭제 20,000건이다. 무료 한도 초과 시 추가 결제보다 방명록 요청 실패·이용 제한을 감수한다. 일일 할당량은 태평양 시간 자정 전후 초기화된다.
- 월 1,000원은 앱의 운영 예산이며 Firebase에 설정한 자동 결제 차단액이 아니다. 실제 콘솔 예산·알림이나 결제 설정은 아직 변경하지 않았다. Vercel도 기존 플랜의 무료 범위 안에서 운영하며 사용량을 별도로 확인한다.
- 자동 TTL 삭제·관리형 백업·PITR·Cloud Functions 등 과금 연결이 필요한 기능은 첫 출시에서 사용하지 않는다. 자동 백업·시점 복구를 제공하지 않는 한계를 기록한다. 복구 기능이 필요해지면 비용을 검토한 뒤 별도 결정한다.
- 보관 기한은 서버가 정한 `expiresAt`으로 관리한다. 승인 대기 30일, 숨김 전환 후 30일을 기본 제안으로 유지하며 공개 글에는 해당 만료를 해제한다.
- 기한 지난 글은 콘솔에서 승인하지 않는다. 공개 API도 만료된 글을 반환하지 않고, 요청 제한 기록은 기한이 지나면 논리적으로 무효화한다. 물리 삭제는 Vercel Cron에서 하루 한 번 서버 정리 함수로 수행한다. 스케줄 요청은 서버 비밀값으로 인증하고 일반 방문자는 실행할 수 없게 한다. Vercel의 무료 플랜 실행 빈도·함수 사용량 범위 안에서 운영한다.
- 일일 정리는 만료된 글·요청 제한 기록·보관 기한이 지난 신고와 삭제된 글의 잔여 신고를 소량씩 처리한다. 신고 보관 기한은 대상 글 삭제 시 또는 처리 완료 후 30일로 제안한다. 문서 삭제는 무료 일일 삭제량에 포함된다. 작업 결과를 확인하고 실패·할당량 초과 시 운영자가 콘솔과 서버 작업으로 복구한다. 정확한 시각의 물리 삭제를 약속하지 않는다.
- 정리 시 글의 하위 컬렉션 자동 삭제에 의존하지 않고 연결된 신고 등을 명시적으로 정리한다. 정리 실패가 기존 설문 동작에 영향을 주지 않게 한다.

### 필수 방어와 안정성

- 클라이언트와 별개로 서버에서 허용 필드·유형·길이를 검증하고 글을 텍스트로 출력한다.
- 등록·신고 요청 제한은 서버리스 인스턴스 간 공유되는 저장소나 플랫폼 기능으로 처리한다. 프로세스 메모리만으로 제한하지 않는다.
- 첫 출시는 등록을 단기 익명 식별값당 10분에 3회로 제한하는 안을 제안한다. 교회 공동 와이파이에서 다수가 작성할 수 있으므로 IP 단독 제한은 넉넉한 보조 방어로 사용하고 실제 오탐에 맞춰 조정한다.
- 방어용 숨김 입력과 서버 측 검증을 두고, 자동 등록이 지속될 경우 추가 봇 검증을 도입한다.
- 앱에 승인·숨김·운영자 삭제 엔드포인트를 노출하지 않는다. 작성자 삭제와 정리 작업에는 각각의 권한 검증을 적용한다.
- 공개 조회는 승인 조건을 DB 조회에서 강제하며, 목록·삭제 응답은 첫 출시에서 캐시하지 않는다. 콘솔에서 상태를 바꾼 뒤 다음 조회에 즉시 반영하되 이미 열려 있는 화면은 재조회가 필요하다. 숨김·삭제 후 공개 캐시에도 남지 않게 처리한다.
- DB 또는 API 장애가 설문·리포트·성찰 사용을 막지 않게 한다. 작성 중 오류에는 재시도 안내를 제공한다.
- 작성·삭제·운영 상태 변경의 동시 요청이 중복 글을 만들거나 삭제된 글을 다시 공개하지 않게 한다.
- 삭제용 화면은 기존 `#/guestbook`과 구분하고, 기존 공유 결과 쿼리 파싱과 충돌하지 않게 설계한다.

## 9. 첫 출시 범위

**포함:** 익명 작성, 선택 별명·모임명, 승인 후 공개, 최신순 목록, 작성자 삭제, 신고, Firebase 콘솔 직접 관리, 입력 검증·요청 제한, 개인정보 안내, 키보드·화면 읽기 접근성.

**후속 검토:** 교회별 페이지, 공식 교회 인증, 지역 지도, 사진, 계정, 댓글·반응, 검색·필터. 실제 사용 수요가 확인되기 전에는 만들지 않는다.

## 10. 완료 기준과 확인 방법

1. 개인·교회·방문자 모두 가입 없이 작성하고, 별명·모임명 생략이 가능하다.
2. 승인 전 글은 공개 API와 화면에서 보이지 않으며 관리자만 조회·처리한다.
3. 설문 답변·점수·성찰 문구가 등록 요청이나 저장 데이터에 포함되지 않는다.
4. 길이 초과, 공백 본문, 잘못된 유형을 서버가 거절하며 HTML 입력을 실행하지 않는다.
5. 중복 제출·네트워크 재시도로 중복 글이 생기지 않으며 오류 후 입력 내용을 유지한다.
6. 삭제 링크 방문만으로 삭제되지 않고, 올바른 토큰의 확인 요청만 삭제를 수행한다.
7. 숨김·삭제 글이 목록·캐시에서 사라지고 보관 기한 정리가 실행된다.
8. 신고·등록 제한, 작성자 삭제 권한, 정리 작업 인증이 서버에서 동작한다. 운영은 권한 있는 Google 계정만 콘솔에서 수행하며 앱에는 관리 API가 없다.
9. 모바일·키보드로 작성·읽기·신고가 가능하며 필드 오류와 등록 상태가 보조기기에 전달된다.
10. 방명록 장애 시에도 기존 설문 흐름이 정상 동작하고 기존 테스트가 통과한다.

증명은 API 권한·검증·상태 전이·중복 요청 테스트, 핵심 작성/승인/삭제 흐름 테스트, 모바일·키보드 수동 확인으로 구성한다. Firestore Emulator에서 직접 클라이언트 접근 거절, 트랜잭션 중복 방지, 삭제와 승인 동시 처리, 만료 기록 무효화를 확인한다. 실제 배포 환경에서는 서울 리전·Spark 플랜·복합 인덱스·서버 IAM 권한·환경 분리·정리 작업·콘솔 승인/숨김/삭제 절차를 확인한다. 무료 할당량 초과 시 기존 설문은 유지되고 방명록에는 일시 이용 제한 안내가 나타나는지 확인한다.

출시 후에는 승인된 실제 글의 내용, 교회·개인 활용 사례, 대기 처리 시간, 스팸·삭제 요청 빈도를 확인한다. 별도 방문 추적 도구 없이 운영 데이터부터 사용하며 글 수를 신앙적 성과나 교회 참여 순위로 해석하지 않는다.

## 11. 확정 사항과 출시 전 준비

**확정:** Firestore Standard, 서울 `asia-northeast3`, Spark 무료 플랜, 월 0원 목표·1,000원 운영 예산, 사용자 본인이 Firebase 콘솔에서 직접 검토·관리.

1. Firebase 프로젝트 식별값과 서울 DB 생성 여부 확인, Vercel 서버 자격 증명 연결
2. 운영자의 실제 확인 주기, 삭제 문의 경로, 중복 요청 기록 보관 기간 확정
3. 콘솔에서 상태·시각·만료 필드를 수정하는 절차 문서와 일일 무료 정리 작업 준비
4. 개인정보 안내·인프라 로그 보관 정책과 자동 백업 미제공 사실 확인

그 외 UI 세부 사항은 기존 모바일 중심 화면과 성찰 화면의 차분한 톤을 따른다.
